# SPEC-06: Real-Time World Server and Spacemap

## Scope and evidence

This specifies the **local emulator** in `Features/World`: its provisional TCP listener, shared world state, and browser page reached through `action=internalMapRevolution`. The command numbers and JSON below are emulator contracts, not confirmed official Unity wire contracts. `docs/world-protocol.md` records incremental loopback and local HTTP evidence. World units are integer map coordinates; speed is units per second; server state is authoritative.

## Listener options and binding

`WorldServerOptions` binds from configuration section `WorldServer`. The defaults are: `Enabled=false`, `Host="127.0.0.1"`, `Port=60954`, `DynamicTcpPort=false`, `DynamicTcpPortRange=null`, `Version="local-1"` and `MaximumPacketBytes=65536`. The defaults are valid. `Validate()` throws `InvalidOperationException("Invalid loopback WorldServer configuration.")` if any of these rules fails:

- `Host` must be exactly the ordinal string `127.0.0.1`. Hostnames, other loopback addresses, IPv6, wildcards and padded values are rejected.
- `Port` must be 0..65535. A fixed listener (`DynamicTcpPort=false`) also rejects port 0. A dynamic listener accepts any in-range port, but ignores it when binding.
- `DynamicTcpPortRange` is allowed only when `DynamicTcpPort=true`. When present, it must parse with `TryGetPortRange`. `null` means "no range". An empty or blank string counts as present and invalid.
- `MaximumPacketBytes` must be 64..1,048,576 inclusive.
- `Version` must not be null or whitespace, and must be at most 64 UTF-16 characters. Surrounding spaces are allowed and kept.

`TryGetPortRange` returns `false` with `(0, 0)` for null or blank input. Otherwise it splits on `-` with entry trimming and requires exactly two invariant-culture decimal integers with an optional ASCII `+` sign. The first port must be at least 1024, the last at most 65535, the last not below the first, and `last - first <= 1023`, so a range holds at most 1,024 ports. A single-port range such as `1024-1024` is valid. Process culture cannot change the accepted syntax: localized positive signs, grouping separators and non-ASCII digits are rejected. Ranges that are reversed, start below 1024, end past 65535, span 1,025 or more ports, have one or three parts, or contain non-numeric parts are rejected. Every rejected range returns `(0, 0)` output bounds, including one whose first number parsed successfully. Validation does not change any option. `WorldServerOptionsSpecificationTests` covers culture independence and failure output; the architecture fixture requires invariant parsing and delayed output assignment.

`WorldServerHostedService.ExecuteAsync` validates first, so a disabled listener with an invalid configuration still fails. Only after that does it return when `Enabled=false`. A dynamic listener with a range tries `IPAddress.Loopback` on each port in ascending inclusive order. It skips a port only on `AddressAlreadyInUse`; any other socket error fails startup. If every port is taken, it throws `No world TCP port is available in the configured range.` The exhausted range must leave `ActualPort` and the configured port unpublished at zero. Without a range, the listener binds loopback port 0 when dynamic, or `Port` when fixed. The bound port is written back to `options.Port` and published as `ActualPort` before the first accept; a loopback client can then connect to that port. The mesh heartbeat host waits for that value before publishing presence. On shutdown, `StopAsync` stops the listener before waiting for the background task, so a pending accept can finish. The listener never binds a non-loopback address. `WorldServerOptionsSpecificationTests` covers option bounds and live socket binding. The architecture fixture checks validation, binding, publish and shutdown order.

For both dynamic modes, the incoming `Port` value is only validated as a legal TCP port; it is never a binding preference. With no range, even an occupied nonzero configured port does not block startup: the listener asks the OS for port 0 and then replaces `Port` with the assigned port. With a range, even a configured port outside that range is ignored: the listener binds the first available in-range port and publishes it to both `Port` and `ActualPort`. Neither mode writes `Port` before successful binding. Live socket tests cover an occupied configured port and an out-of-range configured port; the architecture fixture enforces one post-bind assignment.

For an inclusive two-port range, the first available port wins: if the first port is occupied, the listener releases its failed candidate and binds the second; if the second is occupied, it binds the first without probing the later port. In either case `ActualPort` and the mutable configured `Port` equal the bound port, and a loopback TCP client can connect. The range branch has no ephemeral-port fallback. Socket tests reserve adjacent ports locally and verify both occupancy orders; the architecture test pins the filtered retry, failed-candidate cleanup and range-exhaustion throw.

When both adjacent ports are occupied, the range is exhausted after the second `AddressAlreadyInUse` failure. Startup faults with the exact range-exhaustion `InvalidOperationException`; `ActualPort` and the configured `Port` remain zero. It must not bind an ephemeral port. `WorldServerOptionsSpecificationTests` reserves both loopback sockets throughout this failure check.

Startup outcomes outside the range branch are also fixed. A disabled listener with a valid configuration completes `ExecuteTask` successfully without binding any socket; `ActualPort` stays 0 and the configured `Port` (for example 4321) is left unchanged. A disabled listener with an invalid configuration (for example `Host="localhost"`) faults `ExecuteTask` with `Invalid loopback WorldServer configuration.` before the enabled gate, again without publishing or rewriting the port. A fixed listener (`DynamicTcpPort=false`) binds exactly the configured loopback `Port`, publishes it unchanged as `ActualPort`, and accepts a loopback client there. If that fixed port is already in use, the `SocketException` with `SocketError.AddressAlreadyInUse` propagates unwrapped out of `ExecuteTask`: there is no retry, no ephemeral-port fallback and no `InvalidOperationException` wrapping, `ActualPort` stays 0 and `Port` keeps its configured value. `WorldServerOptionsSpecificationTests` covers each of these four outcomes with live loopback sockets.

For either a fixed listener or a dynamic single-port range, stopping an idle listener must interrupt its pending accept, complete `ExecuteTask` successfully, and release the bound loopback port so a new listener can bind it. `StopAsync` marks shutdown before closing the socket and awaiting background shutdown. The accept loop passes the stopping token to `AcceptTcpClientAsync`; it treats `OperationCanceledException` as normal only when that token was canceled, and treats `SocketException` or `ObjectDisposedException` as normal only after shutdown was marked. Other accept errors must fault the task. The listener closes in `finally`. The live socket tests verify release and successful task completion for both binding modes; the architecture fixture pins the guarded exception paths and cleanup order.

## TCP framing and payload schemas

`WorldPacketCodec` frames packets as `int32BE bodyLength | uint16BE commandId | payload`. Body length includes the two command bytes, must be 2..65,536 by default, and is read exactly across split stream reads. EOF before a header returns null; truncated packets and invalid lengths fail. Writers reject payloads above `maximumPacketBytes-2`. Payload integers are big endian. Strings are `uint16BE UTF8ByteLength | strict UTF-8 bytes`, limited to 1,024 bytes; admin results permit 60,000 bytes. Decoding rejects trailing bytes, truncated strings, and malformed UTF-8. Admitted connections serialize writes.

At the default frame limit, a 65,534-byte payload plus the two-byte command produces a 65,536-byte body and a 65,540-byte total frame; the reader returns that payload intact and begins the next frame at the following byte. A 65,535-byte payload is rejected before the writer allocates or writes a frame. A declared body length of 65,537 is rejected after its four-byte header and before body allocation or consumption, even if body bytes follow. The reader likewise rejects lengths below two before reading a body. These are codec bounds, independent of whether a command is recognized by the session handler. `WorldAndSpacemapSpecificationTests` checks both sides of the default limit and the following-frame boundary; `ApiServiceVerticalSliceTests` pins limit validation ahead of allocation and body I/O in the World slice.

The configured `MaximumPacketBytes` applies symmetrically to inbound and outbound frames in `WorldSessionHandler`. At either permitted option boundary (64 or 1,048,576 bytes), a body exactly that size is accepted: its payload is two bytes shorter, the next frame remains readable, and EOF follows that frame. An outbound payload one byte longer is rejected without writing anything; an inbound declared body one byte longer is rejected after exactly four header bytes, leaving any following body byte unread. The option limit counts the command bytes but excludes the four-byte header. The feature fixture exercises both option boundaries, and the architecture fixture requires the session handler to pass the configured limit to both codec directions.

At the frame boundary, an empty payload has body length 2 and is valid. A payload of exactly `maximumPacketBytes-2` bytes is valid; one byte more fails before any write. A stream that ends before the first header byte returns no packet, while EOF after 1–3 header bytes or within a declared body throws `EndOfStreamException`. Body lengths below 2 or above the configured maximum throw `InvalidDataException`. The codec preserves an unknown `uint16` command value for the session handler to classify; it does not reinterpret its payload. Published command IDs currently occupy the unique, contiguous range 1..40; IDs 38..40 are provisional emulator commands.

The reader may receive a header or body one byte at a time. It assembles exactly one declared frame per call and leaves subsequent frames for later reads; clean EOF is reported only on the next call after the final complete frame. Length validation occurs after the four-byte header and before any body byte is read. A writer rejects an oversized payload before writing any frame bytes. Framing operates on `Stream` within the World slice and has no HTTP transport dependency.

Each read allocates a fresh body buffer. The returned payload is a view of that completed buffer, so reading another frame does not overwrite an earlier packet's payload. Each write copies the caller's payload into a new frame before awaiting the stream write. Mutating the caller's byte array while that write is blocked cannot change the bytes eventually handed to the stream. The writer passes the entire header, command and payload in one stream write call; stream failures can still leave a partial transport write. The feature tests exercise the ownership boundary across a blocked write and consecutive reads, and the architecture fixture pins allocation and copy order.

The caller's cancellation token governs every asynchronous frame I/O operation: the initial header read, completion of a partial header, the exact body read, and the single frame write. Cancellation while any read is blocked propagates `OperationCanceledException`; it is not translated into clean EOF or a truncated-frame error. A write canceled before it begins leaves the stream empty. A canceled read may already have consumed part of a frame, so the caller must discard that transport rather than resume parsing from the middle. A write canceled after its stream accepts bytes likewise has no rollback guarantee. `WorldAndSpacemapSpecificationTests` exercises cancellation before a header byte, after two header bytes, after the complete header and command, and before a write. The architecture fixture checks token forwarding at every codec I/O site.

After authentication, an admin command is a single ordinary length-prefixed UTF-8 string and must consume the whole packet payload. For an authorized pilot, invalid UTF-8, a truncated declared string, or trailing bytes produces one `LoginErrorCommand` with the single-byte `Malformed` code (1), then ends the connection without dispatching the command. The authorization check runs before payload decoding, so an unauthorized pilot receives `Unauthorized` (8) instead and remains connected for later requests. The same malformed-payload boundary also handles fixed-width authenticated requests. `WorldTransportTests` checks the three malformed admin payloads and unauthorized precedence over a loopback TCP connection; the architecture fixture guards the strict decoder exception in the authenticated handler branch.

String limits count UTF-8 bytes rather than characters: 512 two-byte characters fill the ordinary 1,024-byte limit. The two-byte length prefix is big endian. A declared length beyond the relevant limit throws `InvalidDataException`; too few bytes throw `EndOfStreamException`; invalid UTF-8 throws `DecoderFallbackException`. Admin-result strings use the same encoding with a separate 60,000-byte limit. `WorldPayload.Decode` requires the decoder to consume the complete payload.

Both ordinary and admin-result writers encode with strict UTF-8. An unpaired UTF-16 surrogate throws `EncoderFallbackException` before its length prefix or content is written; it is never replaced by U+FFFD. Empty strings encode as `00 00`. A complete four-byte scalar counts as four bytes toward either limit; exactly 1,024 ordinary bytes or 60,000 admin-result bytes are accepted, and one additional byte is rejected. Both readers reject overlong sequences, encoded surrogate code points, values above U+10FFFF, and incomplete multi-byte scalars with `DecoderFallbackException` when the declared bytes are present. A declared length whose bytes are missing instead throws `EndOfStreamException`. These are provisional emulator wire rules.

Signed `i32` and `i64` fields occupy exactly four and eight bytes in big-endian two's-complement order, including zero and both signed bounds; no padding or variable-length integer encoding is permitted. Reading any shorter field throws `EndOfStreamException`. `WorldPayload.Decode` accepts an empty payload only when the supplied decoder consumes nothing; any byte left after that decoder returns, including a single byte after an otherwise complete integer, throws `InvalidDataException`. The decoder's return value does not waive this full-consumption check.

TCP login resolution applies these guards in order after the login packet is decoded: a null, empty, whitespace-only, or longer-than-128-character `dosid` returns `UnknownSession` without reading the session store; exactly 128 characters is allowed and passed through unchanged. A missing stored session returns `UnknownSession`. An expired session (expiry at or before current UTC time) returns `ExpiredSession` before user or company checks. A nonpositive or different requested user ID returns `UserMismatch`; a missing or unrecognized company returns `CompanyRequired`. All failures precede account state lookup. Success reads the active hangar slot, ship, credits and uridium once, then reads details for that same slot once. The pilot projects the catalog's starter map and faction with the stored account ID, username and admin flag, plus the account balances, stats, experience, honor, level, configuration-two stats and speed, base speed, and both companion lists. The owner-name admin exception remains an emulator rule. `WorldPilotResolverSpecificationTests` covers the token boundary, error precedence, lookup suppression and detailed projection; the architecture fixture pins the resolver to this world slice and its ordered guards.

The entry burst is map, station, each gate, safe-zone flag, then hero. Login follows a matching version request. A local jump emits map change followed by a new entry burst; a remote owner receives handoff. TCP packet definitions remain provisional.

Before login, each well-formed `VersionRequest` replaces the connection's previous version-accepted state. The server answers with `VersionCommand(str configuredVersion, u8 accepted)`; an unmatched request yields `accepted=0` and leaves the socket open for another version request, while a later exact match yields `accepted=1`. A later mismatch revokes earlier acceptance. No version request resolves an account. A `LoginRequest` first requires that accepted handshake, then decodes `i64 userId, str dosid, str version, str instanceId` with full payload consumption. The login's own version must still equal the configured version and its instance ID must contain 1–128 UTF-16 characters; zero or 129 characters are rejected. A failed login handshake, login-version, or instance-ID gate returns `LoginErrorCommand(UnsupportedVersion=2)` and ends the session handler before `IWorldPilotResolver.ResolveAsync`. The login-version gate is therefore independent of the earlier accepted version request. `WorldTransportTests` exercises both retry directions, successful login, rejected login version and instance-ID boundaries, resolver suppression, and handler completion; `ApiServiceVerticalSliceTests` pins the guard order inside the World session handler. These are provisional emulator handshake rules, not captured Unity behavior.

A prelogin `VersionRequest` must contain exactly one ordinary string. A truncated two-byte length prefix, malformed UTF-8, or trailing payload byte produces one `LoginErrorCommand(Malformed=1)` and ends the handler without a version response or identity lookup. After an accepted version, the same malformed boundary applies to the `LoginRequest`'s fixed-width user ID and three strings, including a truncated ID, invalid UTF-8, and trailing bytes. Before a version is accepted, the handshake gate takes precedence over login payload decoding: even a malformed login payload returns `UnsupportedVersion=2`. `WorldTransportTests` pins these responses and successful handler completion on live loopback sockets; `ApiServiceVerticalSliceTests` guards decoding, handshake, and resolver order. These remain provisional emulator rules.

Before admission, every command ID except `VersionRequest` and `LoginRequest` returns exactly one `LoginErrorCommand(UnknownCommand=7)` and ends the handler. This holds whether a version was accepted and whether the command ID is known in another phase or absent from the enum. The command payload is not decoded, so malformed bytes do not turn this error into `Malformed`; identity resolution is never attempted. `WorldTransportTests` exercises known response and gameplay IDs plus an undefined ID over loopback, and `ApiServiceVerticalSliceTests` pins the dispatch fallback ahead of the malformed-payload catch. This is a provisional emulator rule.

After successful authentication and the entry burst, a command ID without an active handler returns exactly one `LoginErrorCommand(UnknownCommand=7)` and ends the session handler. This includes handshake IDs (`VersionRequest`, `LoginRequest`), response-only IDs, gameplay IDs whose required service is unavailable, and undefined IDs. The payload is not decoded, so malformed bytes do not change the result to `Malformed`; the pilot resolver is not called again. `WorldTransportTests` exercises these categories on a loopback socket, while `ApiServiceVerticalSliceTests` guards the authenticated fallback after the payload-error boundary. This is provisional emulator behavior, not a captured Unity contract.

### Entry burst projection

`WorldEntryPackets.SendAsync` uses the supplied runtime map, or `WorldMapInstance.Starter(pilot.MapId)` when absent. Map initialization sends that map's ID, width, height and faction; station sends its ID, position and peace radius. It sends one gate packet per portal in list order with ID, position and destination map ID. Portal arrival coordinates and jump radius are not entry packet fields. A map with no portals sends no gate packet. The safe-zone packet is exactly one byte: 1 when the **effective** position lies within the station's inclusive squared radius, otherwise 0. The effective position is the supplied position override or the pilot's saved X/Y. Both coordinate differences are widened before subtraction, and their squared sum and the squared radius use 128-bit arithmetic. Thus opposite `int` extremes cannot wrap into the peace zone, while a point exactly on the radius is inside it.

The final hero packet retains pilot identity, faction, map ID, economy, level and hangar slot. Its X/Y use the same effective position as safe zone. Speed, maxima, cargo capacity, laser damage and equipment come from supplied active stats or `pilot.Stats`; current HP defaults to the chosen maximum HP, and current shield defaults to the chosen maximum shield. The current cargo load is the literal zero. Equipment count precedes `(itemId, quantity)` pairs in assignment order. Values are encoded as supplied, without clamping by this emitter. The burst does not change the pilot record. Login and jump paths call this shared World-slice emitter, so their packet order and field projection stay aligned. `WorldEntryPacketSpecificationTests` covers runtime-map replacement, zero/two-gate bursts, inclusive and extreme-coordinate radius boundaries, full hero field order and default versus explicit vitals.

Each `WorldConnection` serializes outgoing packets for its socket with a semaphore held through the entire asynchronous frame write. If a first write is suspended, a second send waits without writing header or payload bytes. Once released, the reader observes the two complete frames in send order. The gate is released in `finally`, including when writing fails or is canceled; it is per connection, not a global lock across sockets. The frame writer issues one write for the complete header, command and payload, so no packet bytes from different sends can interleave on a connection.

Cancellation also governs admission to that per-socket gate. A send canceled while another frame holds the gate throws `OperationCanceledException` without calling the stream writer; the active frame and a later send still complete in order. If cancellation interrupts the active stream write before it emits bytes, that send throws `OperationCanceledException` and releases the gate so a later frame can be written. The latter guarantee concerns gate recovery; the codec does not promise to repair a transport that has already accepted a partial frame.

## Movement, tick, station and radiation

Origin is previous same-map travel interpolated at server time, otherwise saved position. Clamp targets to `[0,width]×[0,height]`; an out-of-bounds request sets `radiationWarning`. For distance `d=sqrt((targetX-startX)^2+(targetY-startY)^2)` and speed `v`, `durationMs=0` if `v<=0`, otherwise `ceil(1000d/v)`. At elapsed seconds `t=max(0,(nowMs-startMs)/1000)`, `f=1` when `d=0`, otherwise `clamp(tv/d,0,1)`. Position is `round(start+(target-start)f)` per coordinate. A new move receives a GUID revision. HTTP `expectedMoveId` rejects stale same-map moves; `mapId` rejects old-map commands. Configuration and runtime speed changes retime remaining travel from current position.

Movement edge cases: map bounds are inclusive, so a target of exactly (21,000, 13,100) is accepted without a warning; -1 or height+1 is clamped and sets the warning. Zero speed or zero distance gives `durationMs=0`. Travel saved on another map is ignored, so the move starts from the pilot's saved `X/Y`. Each `Travel` call issues a fresh non-empty `MoveId` even for the same move result. Server time before `StartedAtUnixMilliseconds` resolves to the start position.

`WorldMovement.Begin` widens each target coordinate before subtracting the saved or interpolated origin. This keeps distance nonnegative even when a saved position spans opposite signed 32-bit extremes. For positive speed, duration is the ceiling of distance × 1,000 / speed, saturated at `Int32.MaxValue` milliseconds before encoding as an `i32`; speed zero or below gives zero. A saved origin outside the map does not itself set `radiationWarning`: that flag describes only whether the requested target was outside map bounds. The extreme-coordinate feature tests cover saved and same-map-travel origins, finite high-speed duration, saturation, and zero speed. The architecture fixture pins widening before subtraction and saturation before conversion.

Interpolation rounds each coordinate with .NET's default midpoint-to-even rule after clamping progress to 0..1. A same-map retarget computes both its duration and its new travel origin from the previous trip's position at the command time; it leaves the previous travel record intact and assigns a new revision. If that previous trip has a future start time, its recorded origin is used, and the replacement trip starts at the current server time. The pure movement calculation stays in the World slice, separate from HTTP and persistence.

Stored travel origins are doubles, even though observed positions and move targets are integers. At the start of a trip, a fractional origin is rounded per coordinate with midpoint-to-even, including negative halves; for example `(1.5, 2.5)` resolves to `(2, 2)` and `(0.5, -0.5)` resolves to `(0, 0)`. A nonpositive-speed trip retains that rounded origin even after its nominal target time. Retargeting a same-map trip uses this integer `PositionAt(now)` result for both the next duration and the next travel record's origin; it never calculates either from the raw fractional fields. The prior record remains unchanged. The fractional-origin feature cases and the World-slice architecture invariant pin this projection boundary.

For a travel record with distinct origin and target, speed zero or below clamps progress to zero at every nonnegative elapsed time, including a day after its start: `PositionAt` stays at the recorded origin. A zero-distance record instead resolves to its target immediately because its progress is defined as one. `Begin` reports zero duration for a nonpositive requested speed even when the target differs. Both `Begin` and `Travel` choose the same origin rule: interpolate a prior record only when its map equals the pilot's current map; otherwise use the pilot's saved coordinates. A same-map stationary record therefore supplies its original coordinates when retargeted, while a foreign-map record cannot affect either duration or the new travel origin. Feature and architecture tests pin these conditions.

The NPC simulation sleeps `world.tick_rate_ms` (default 1,000 ms), then current map lease owners broadcast NPC spawn/movement and manual boxes. NPC positions derive from UTC time and do not accumulate tick drift. TCP observer NPC and remote-pilot snapshots are 500 ms presentation caches; combat reads authoritative shared vitality. Presence heartbeats run at 15-second intervals.

An observer on another replica may display the pre-hit NPC shield until its 500 ms snapshot expires. After expiry, a fresh state poll must show the shared hit vitality or omit a destroyed NPC, provided the NPC respawn cycle has not changed. The live HTTP and page test advances a common clock past snapshot expiry without crossing a respawn boundary, so it distinguishes cache refresh from normal cycle reset.

Safe zone uses `dx²+dy²<=peaceRadius²`. A stationary pilot inside the radius repairs hull to maximum by `world.station.repair_hp_per_tick` or `max(1,maxHp/50)` if unset/nonpositive, and recharges shield by `max(1,maxShield/50)` per repair call. A full hull does not prevent shield recharge. Traveling or distant pilots do not repair. A clamped out-of-bounds move applies damage at most once per second: `world.radiation.damage_per_attempt` or `max(1,maxHp/100)` if zero/default, leaving at least 1 HP. The radiation feature is a boundary warning/damage rule, not a separate traversable zone.

The one-second radiation interval is inclusive at its end: an additional out-of-bounds move at 999 ms after damage cannot harm the hull, while one at 1,000 ms can. Repeated attempts stop at 1 HP. The station boundary itself qualifies for repair; one map unit outside does not. A pilot whose current position is inside the station radius still waits until its travel reaches its destination before repair. Damage and repair are saved in the shared runtime snapshot. The fenced repair path checks the map lease and refreshes shared pilot state before writing so state polling cannot repair a pilot after map ownership changes.

## Ships, configurations and companions

The starter assignment is Pusat Plus in slot 1 (128,000 HP, speed 370, cargo 1,500) and Phoenix in slot 2 (4,000 HP, speed 320, cargo 100). World entry reads each account's active slot and assigned ship from PostgreSQL. A recognized assigned ship determines hull, cargo, base speed, and live speed variable even when it occupies the other slot; equipment still belongs to its assigned slot. Unknown ship IDs retain that slot's local defaults because the ship catalog has no combat stat columns. Configurations 1 and 2 independently use owned, positive-quantity assignments for that slot. `WorldShipStatCalculator` computes `speed=baseSpeed+Σ(generator speed×quantity)`, `maxHp=baseHp×(100+hullSkillBonus)/100`, `maxShield=Σ(shield×quantity)×(100+shieldSkillBonus)/100`, and `laserDamage=Σ(damage×quantity)×(100+laserSkillBonus)/100`, with integer truncation. Built-in item defaults: LF2 100, LF3 150 damage; SG3N-A03 3,000, SG3N-B02 5,000 shield; G3N-1010/2010/3010/3310 add 10/20/30/40 speed. Valid numeric catalog overrides (0..1,000,000) take precedence. Invalid configuration throws.

Catalog stat resolution is per assigned item and requested field (`damage`, `shield`, or `speed`). It selects the **first** listing whose `ItemId` matches exactly, then accepts that field only when the stats value is a JSON object containing a nonnegative Int32 integer at most 1,000,000. Zero is an authoritative override. If the field is absent or invalid, the built-in value for that item and field applies; a later duplicate listing is not consulted. Any assigned item with a valid requested field contributes to that stat, regardless of its usual equipment type. Other fields on the selected listing do not leak into the requested stat, and unassigned catalog items make no contribution. `WorldAndSpacemapSpecificationTests` covers per-field isolation, the zero and maximum boundaries, and first-listing fallback; the architecture fixture pins the lookup and validation in the pure World calculator.

Stat edge cases: an override applies only if it is a JSON number that fits `Int32` and lies in 0..1,000,000. `0` and `1000000` win; `-1`, `1000001`, `1.5` and the string `"500"` fall back to the built-in default. An assignment counts only if its quantity is positive and the owned inventory quantity covers it in full; otherwise the whole assignment is dropped, not capped. `Equipment` lists the counted assignments in their original order. Hull, shield and laser skills add 2% per rank, with ranks clamped to 0..5 (maximum +10%). An explicit `baseSpeed` replaces the hull base speed before generator bonuses. Configurations other than 1 and 2 (including 0 and negative values) throw `ArgumentOutOfRangeException`. Switching has a five-second cooldown and preserves travel continuity; current shield is scaled to the new maximum (or filled if the old maximum was zero). Current hull is retained.

Owned `drone_flax` and `drone_iris` assignments yield up to the hangar drone-slot limit. A `pet_10` companion requires assignment and ownership in the active configuration, `Enabled=true`, and positive fuel. Standard/arrow/line formations position companions relative to the interpolated ship and clamp to map bounds. Drones and P.E.T. are visual companions here, not independent combatants.

### Companion derivation and formation geometry

`WorldCompanions` is a pure, synchronous projection. `WorldSessionHandler` is its only caller for `FromEquipment` (once for configuration 1 and once for configuration 2 at world entry), and `WorldState` is its only caller for `At`.

`FromEquipment(equipment, slot, pet, configuration = 1)`:

- Drone candidates are assignments for exactly that hangar slot and configuration whose `ItemId` is exactly `drone_flax` or `drone_iris` (case-sensitive; other drone IDs and `pet_10` never become drones), with `Quantity > 0`. They are processed in assignment order.
- An assignment counts only if a single inventory row with the same ID holds at least the assigned quantity. A short assignment is dropped entirely, not capped. Ownership is checked per assignment, not cumulatively: two assignments of 2 against an inventory of 2 both count.
- Duplicate inventory rows are not summed for this check. Two rows of one drone do not cover an assignment of two; a later row of two or more does cover it even if an earlier row is short. Item IDs match exactly, including case. `WorldCompanionSpecificationTests.FromEquipment_DoesNotCombineSplitInventoryRowsToSatisfyDroneAssignment` and `FromEquipment_UsesAnySingleSufficientInventoryRowRegardlessOfRowOrder` pin this boundary; the World architecture invariant retains the per-row `Any` predicate.
- Each counted assignment adds one `drone` per unit until `LocalHangarEquipmentStore.DroneSlots` (10) drones exist. `Index` is the running drone count (0..9) across assignments.
- A single `pet` (`pet_10`, `Index` 0) is appended last, after any drone cap, only if `pet.Enabled`, `pet.Fuel > 0`, the active slot and configuration have a `pet_10` assignment with positive quantity, and the inventory holds at least one positive `pet_10` row. The assigned pet quantity doesn't need to be fully owned.
- P.E.T. assignment and inventory IDs match exactly and case-sensitively. A `PET_10` row cannot cover `pet_10`; a zero-quantity exact row cannot cover it either. A later exact positive row qualifies even if earlier rows are empty or have another case. Duplicate positive assignments still produce exactly one P.E.T., and neither their quantities nor separate inventory-row quantities are summed. `WorldCompanionSpecificationTests.FromEquipment_DuplicatePetAssignmentsAndInventoryRowsStillYieldExactlyOnePet` and `FromEquipment_PetRequiresExactPositiveInventoryRowAndAssignment` pin this boundary; the World architecture invariant retains the exact positive predicates and single append.
- Every companion copies `pet.Formation`, whether the P.E.T. is present or not.

`At(companions, x, y)` keeps input order and copies `Kind`, `ItemId`, `Index` and `Formation`. `drones` counts only `drone` entries. Offsets from the ship:

| Kind / formation | `dx` | `dy` |
| :--- | :--- | :--- |
| `pet` (any formation) | `-75` | `55` |
| `arrow` | `-45 - 22×(i/2)` | `(i even ? -1 : 1) × (28 + 20×(i/2))` |
| `line` | `-60` | `(i - (drones-1)/2) × 30` (integer division, so even counts skew downward: 4 drones → −30, 0, 30, 60) |
| any other value (`standard`, `""`, `Arrow`, unknown) | `round(65·cos θ)` | `round(65·sin θ)`, `θ = π(i+1)/(drones+1)` |

Formation names are case-sensitive. A single standard drone sits at `(0, 65)`. Three sit at `(46, 46)`, `(0, 65)`, `(-46, 46)`. Add each offset to the ship coordinate in widened signed arithmetic before clamping to the inclusive map bounds `0..21000` × `0..13100`; even `Int32.MinValue` and `Int32.MaxValue` ship coordinates cannot wrap to the opposite map edge. An empty list yields an empty list. `WorldCompanionSpecificationTests.At_ExtremeShipCoordinates_ClampAfterWidenedOffsetAddition` covers all four combinations of signed coordinate extremes, and `ApiServiceVerticalSliceTests.WorldCompanions_ArePureProjections_BuiltAtEntryAndPositionedOnlyByWorldState` preserves the widened projection.

`At` positions entries in input order without assigning new indexes or normalizing formations. It counts entries whose kind is exactly `drone` for the standard angle denominator, but computes each offset from that entry's stored `Index` and `Formation`. Thus a nonsequential standard drone index 2 among two drones has angle π and offset `(-65, 0)`; two line drones both carrying index 0 occupy the same `(-60, 0)` offset. A P.E.T. uses `(-75, 55)` regardless of its stored index or formation and does not increase the drone count. The output preserves every entry's kind, item ID, index, and formation. `WorldCompanionSpecificationTests.At_UsesStoredDroneIndexesAndEachCompanionsOwnFormation` and `At_DuplicateDroneIndexesProduceIdenticalOffsetsWithoutRenumbering` cover these edge cases; `ApiServiceVerticalSliceTests.WorldCompanionPositioning_UsesStoredIndexesAndPerEntryFormation` pins the projection boundary.

`LocalPetStore` keeps one JSON `LocalPet` per account under `world:pet:{accountId:N}` with a 30-day sliding expiration. A missing record, the JSON literal `null`, malformed JSON, a non-object JSON value, or a value with an incompatible field type reads as `LocalPet(Enabled=false, Fuel=0, Formation="standard")`. This fallback applies only to JSON decoding; cache I/O and cancellation errors still propagate. A damaged account record does not change another account's saved P.E.T. Accounts are isolated. `WorldCompanionSpecificationTests.PetStore_DamagedJsonRecord_FallsBackToInactivePetWithoutAffectingOtherAccounts` covers the record forms, and `ApiServiceVerticalSliceTests.WorldCompanions_ArePureProjections_BuiltAtEntryAndPositionedOnlyByWorldState` guards the narrow exception boundary.

Valid object records may omit fields: absent `Enabled`, `Fuel`, and `Formation` take the constructor defaults `false`, `0`, and `"standard"` independently. The default JSON serializer matches those property names with exact casing; lowercase variants do not set them. Unknown properties are ignored, allowing an extended record to retain the recognized values. An enabled record without `Fuel` remains invisible even when the active hangar owns and assigns `pet_10`; saving positive fuel makes that P.E.T. visible. The cache does not rewrite sparse records during reads. `WorldCompanionSpecificationTests.PetStore_ValidSparseOrExtendedJson_UsesDeclaredDefaultsAndExactPropertyNames` and `PetStore_EnabledWithoutFuel_DoesNotProjectPetUntilPositiveFuelIsSaved` exercise the persistence-to-projection boundary; `ApiServiceVerticalSliceTests.WorldCompanions_ArePureProjections_BuiltAtEntryAndPositionedOnlyByWorldState` pins the default and fuel gate in the World slice.

Writes serialize the three property names `Enabled`, `Fuel`, and `Formation` as JSON using the account-specific key. The cache entry has a 30-day sliding expiration and no absolute expiration. Reads and writes pass the caller's cancellation token to the cache; an I/O or cancellation exception propagates to the caller without being converted to an inactive pet. `WorldCompanionSpecificationTests.PetStore_WriteUsesAccountKeyJsonAndSlidingExpiryWithoutAbsoluteExpiry`, `PetStore_CacheReadFailurePropagatesWithoutDefaulting`, and `PetStore_CacheWriteFailurePropagates` pin these cache boundaries. The architecture fixture keeps the cache read ahead of the JSON-only fallback and forbids an absolute expiry.

### Companion state during travel and configuration changes

`WorldSessionStore.CompanionPositions(pilot, at)` first interpolates the authoritative ship position at `at`, then projects the companions of the current configuration through `WorldCompanions.At`. A position read at a future time does not advance or rewrite travel: reading the start again returns the original positions. At travel completion, positions stay at the destination. The same drone and P.E.T. offsets are applied at every point of the trip. A successful configuration switch immediately replaces the visible companion list; a switch rejected by the five-second cooldown keeps the current list. Switching back after the cooldown restores the first configuration's companions.

The provisional `CompanionState` packet (command 17) is `i64 userId, i32 count`, followed by exactly `count` entries of `str kind, str itemId, i32 index, str formation, i32 x, i32 y, i32 targetX, i32 targetY, i32 durationMs`. Current coordinates come from `CompanionPositions`; target coordinates use the ship destination and the **same active configuration**. Every entry receives the same remaining travel duration; it is zero when no travel record exists. A stationary companion has equal current and target coordinates. Both direct sends and broadcasts use the same packet writer, so their field order and active-configuration choice cannot diverge. Evidence: `WorldCompanionStateSpecificationTests` and `ApiServiceVerticalSliceTests.CompanionState_ProjectsCurrentAndTargetFromSameActiveConfiguration_WithSharedWireWriter`.

Moving and finished travel follow these rules (all checked by `WorldCompanionStateSpecificationTests`):

- **Moving.** Each entry's current position is its formation offset applied to the interpolated ship position at send time, so the offsets between entries stay constant during travel. Each target is the same offset applied to the ship's stored destination. `durationMs` is `ceil(distance × 1000 / speed)`, where distance runs from the ship's current position to its destination and speed is the active configuration's **base** `Speed` (`ActiveStats`, not the skill-adjusted speed used by `MoveAsync`). The clock is the wall clock when the payload is built.
- **Arrived.** A travel record that has reached its destination is not cleared. The packet then reports current = target = the destination plus each entry's offset, with `durationMs = 0`.
- **Out-of-map destination.** Targets come from the **clamped** ship destination (`0..21000 × 0..13100`), not the requested coordinates. For example, a request for `x = 30000` gives a `line` drone a target of `20940`. The duration covers only the clamped distance.
- **Runtime speed changes.** `MoveAsync` saves travel using `max(1, round((activeStats.Speed + currentBaseSpeed - baseSpeedAtLoad) × world.movement.speed_multiplier))`; `CompanionState` instead computes its `durationMs` from the remaining ship distance and `activeStats.Speed`. For a base speed of 100, a 1000-unit move takes 20000 ms at multiplier 0.5 or 5000 ms at multiplier 2, while the packet's remaining duration is the remaining distance times 10 ms. It can therefore understate or overstate actual remaining travel time. The same packet duration is written to every companion entry. This is the current emulator contract, not a captured official protocol rule.

## NPCs and combat

**Provisional emulator contract (native Unity packets unproven).** The map lease owner runs NPC AI on each world tick. Under the mesh mutex, each living NPC chooses the nearest active pilot on its map within `AggroRange=1200` units, breaking ties by user ID. Pilots inside the home station peace radius are excluded. An NPC moves toward that pilot at its template speed in map units per second; elapsed time is capped at five seconds per tick to limit leaps after a pause. Its position, target user ID, last step time, and last fire time are cached with vitality for the current respawn cycle. It fires within `NpcFireRange=650` at most once per `NpcFireCooldownSeconds=2`, with `NpcDamage=40`. Damage depletes shield first, then hull to zero, and persists pilot runtime. `NpcFireCommand` (40) broadcasts the resulting pilot vitals to local TCP observers. Target and pursuit state expire with the respawn cycle.

**Provisional rocket contract.** A selected NPC can be attacked with TCP `RocketFireRequest` (38, `i32 npcId`) or HTTP `POST /spacemap/world/fire` with `{"npcId":123,"weapon":"rocket"}`; omitted `weapon` means laser. Rockets have `RocketRange=1500`, fixed `RocketDamage=250`, and a per-pilot distributed-cache cooldown of `RocketCooldownSeconds=3` starting with a valid in-range shot. A shot during cooldown returns `cooldown` through the existing fire-result command or HTTP 409 response. Rocket hits use command 39 with the laser-hit payload order. Rockets and lasers share shield absorption, NPC vitality, lethal reward snapshot, per-asset idempotency keys, and killer-only retry. Rocket ammo and client-specific rocket types are unproven and are not modeled.

Default per-map templates: Streuner (3, 800 HP, 200 shield, speed 90, reward 400 credits/1 uridium/400 XP/2 honor), Lordakia (2, 2,000 HP, 800 shield, speed 70, reward 800/2/800/4), Saimon (1, 4,000 HP, 1,600 shield, speed 55, reward 1,600/4/1,600/8). ID is `mapId*10000+typeIndex*100+slot+1`; coordinates derive from ID and sine/cosine of UTC time, clamped to map dimensions. Runtime variables can override counts; invalid counts/templates are skipped. Respawn cycle defaults to 300 seconds, minimum 30. Patrol remains deterministic until an NPC acquires a pilot.

Attacks require an account, current map, live NPC or eligible saved kill, and `distance²<=fireRange²` (default range 1,000). TCP also requires target lock, except the original killer retrying credit. `damage=max(1,round(activeLaserDamage×laserMultiplier))`; `absorbed=min(shield,round(damage×clamp(absorptionRatio,0,1)))`; new shield is `max(0,oldShield-absorbed)` and HP is `max(0,oldHp-(damage-absorbed))`. A kill saves killer, NPC/reward snapshots before crediting four idempotent economy assets. The killer can retry failed credit after selection expires, spawn removal, or moving away; another account cannot claim it. Multipliers apply on the kill; retry uses saved amounts. Killed NPCs disappear until the next respawn cycle.

If reward credit throws after a lethal hit, the exception reaches the caller, but the shared kill record already contains zero HP, the killer account, the original NPC, and the adjusted reward values. The NPC stays absent from visible spawns for that cycle. `CanRetryRewardAsync` is true only for that killer; another account's attack returns `destroyed` without invoking reward credit. A killer retry invokes credit with the saved reward and returns `destroyed` without applying more damage. The economy adapter's per-asset idempotency keys handle an uncertain partial credit; the world layer does not mark a separate credit-complete flag.

### NPC packet emitters

`WorldNpcPackets` is a static, pure set of two emitters built only on `WorldPayload`; it performs no I/O, caching or validation of its own.

- `Create(npc)` is the ShipCreate (24) payload: `i32 id, str kind, str shipId, i32 x, y, hp, maxHp, shield, maxShield`. Its length is exactly `4 + (2 + utf8(kind)) + (2 + utf8(shipId)) + 24` bytes. Reward fields (`Credits`, `Uridium`, `Experience`, `Honor`) are never emitted; two NPCs differing only in rewards produce identical bytes.
- `Health(npc)` is the NpcHealth (37) payload: exactly 20 bytes, `i32 id, hp, maxHp, shield, maxShield`. These are byte-for-byte the Create ID followed by Create's trailing 16 bytes. Health does not encode `kind` or `shipId`, so a string that Create would reject never affects Health. Note that TargetLock (26) uses a different vitals order (`hp, shield, maxHp, maxShield`).
- Every `i32` field is copied unclamped, including `int.MinValue`, `-1`, `0` and `int.MaxValue`. Neither emitter checks vital invariants: HP above max HP or a negative shield is emitted as given. Keeping vitals in range is the job of `WorldNpcs`.
- `kind` and `shipId` follow the ordinary string rules. Length is counted in UTF-8 bytes, so `"Ä"` is 2 bytes and U+1F680 is 4. An empty string encodes as `00 00`. Exactly 1,024 bytes are accepted. 1,025 bytes, or 513 two-byte characters, throw `InvalidDataException`. An unpaired surrogate in either string throws `EncoderFallbackException`. In each failure case the emitter throws instead of returning a partial payload.
- Emitters are deterministic and return a fresh array per call, so a caller that mutates one result does not affect later results.
- Call sites send `Create` only under `ShipCreateCommand`: the entry roster burst, idle roster sync for newly visible IDs, and `WorldState.BroadcastNpcSpawnAsync`. They send `Health` only under `NpcHealthCommand`, during idle roster sync when a known NPC's `(hp, shield)` differs from the last vitals sent on that socket.

Evidence: `ThDarkOrbitEmulator.Tests/ClientTesting/WorldNpcPacketSpecificationTests.cs` (wire order, lengths, bounds, string limits, framing) and `ApiServiceVerticalSliceTests.WorldNpcPackets_ArePureWorldPayloadEmitters_SentOnlyUnderTheirCommandIds` (purity, 14 field writes, no reward fields, command-ID pairing at every call site). These are provisional emulator wire rules, not captured client evidence.

### NPC simulation broadcast loop

`WorldNpcSimulationService` is a hosted background loop that consumes map leases. It never heartbeats, drains, acquires or mutates the mesh, and it never builds NPC payloads itself; it only calls the `WorldSessionStore` broadcast methods. Each tick runs in this order:

1. **Pace.** Wait `world.tick_rate_ms` milliseconds (the runtime variable). When no `IRuntimeVariableRegistry` is registered, wait 1,000 ms. The delay comes before any work, so the first emission happens one full tick after start.
2. **Snapshot.** Read `IServerMeshRegistry.GetSnapshotAsync` once per tick. The same snapshot drives pruning and emission.
3. **Announce.** If `WorldAdminEvents` is registered and the latest announcement's `AtUtc` is strictly later than the last one broadcast, broadcast its message once and remember that timestamp. An equal or older timestamp is never re-broadcast. Announcements do not depend on lease ownership.
4. **Resolve ownership.** The node ID is `ClusterOptions.NodeId`. When that is blank or whitespace, it is `{MachineName}-{ProcessId}`, the same fallback `ServerMeshHostedService` uses. A lease is *live-owned* when `NodeId` matches exactly and `ExpiresAtUtc > DateTimeOffset.UtcNow` (strict, so a lease that expires exactly now is not owned).
5. **Prune.** For every map in the known-NPC set that is no longer live-owned, forget its known NPC IDs, known admin-box IDs and respawn cycle. If this node regains the lease later, it starts clean and re-spawns every visible NPC and admin box.
6. **Emit per live-owned lease.**
   - Read `WorldNpcs.VisibleAsync(mapId)`. If the recorded cycle for the map differs from `WorldNpcs.CurrentCycle`, or none is recorded, clear the known-NPC set and record the new cycle. That way NPCs that respawn with the same ID get a new spawn.
   - For each visible NPC: if its ID is new to the known set, broadcast a spawn (ShipCreate) first. Every visible NPC, new or not, then gets a move broadcast in the same tick.
   - Narrow the known set to the visible IDs, so an NPC that disappears and reappears is spawned again.
   - If `WorldCollectibles` is registered, only boxes with `Id < 0` (manual admin boxes) are considered. Each newly seen box is broadcast once with `BroadcastAdminBoxAsync`, and the known-box set is narrowed to the visible boxes. Deterministic cycle boxes (positive IDs) are never pushed by this loop.

Cancellation of the stopping token ends the loop from inside the delay or any awaited call. The loop has no catch, so any other exception stops the hosted service.

Evidence: `ApiServiceVerticalSliceTests.WorldNpcSimulation_EmitsOnlyForLiveOwnedLeases_InTickOrder` (stage order, shared live-owned lease filter used for both prune and emit, full per-map forgetting, 1,000 ms default, read-only lease consumption with no packet building). Runtime emission across sockets is covered indirectly by the world transport tests. This is emulator behaviour, not captured client evidence.

## Collectibles

Each map and 300-second cycle deterministically spawns six slots by default: 200 credits, 5 uridium, 1 galaxy energy, 10 prometium, 8 endurium, 6 terbium. IDs are `mapId*1000+slot+1`; coordinates derive from map, slot and cycle. Count clamps to 0..1,000. Runtime variables override spawn count, respawn seconds and default pickup radius 180. Pickup requires account, current map, existing box, `distance²<=radius²`, unclaimed cycle key and enough cargo for ore. Claim reservation precedes wallet credit to prevent two accounts receiving the box across replicas; uncertain ledger outcomes retain reservation. Credits and uridium use reward multipliers. A new cycle respawns boxes; manual admin boxes are also visible.

For an ore box, `cargoUsed + box.Amount == cargoCapacity` is accepted; only a strictly greater sum returns `cargo_full`. That rejection leaves the box visible and makes no wallet credit call. After a valid pickup reserves the cycle-scoped claim in the shared cache, a wallet exception propagates and the reservation remains. The box is hidden for that cycle, and a retry returns `claimed` without calling the wallet again. This favors at-most-once credit attempts when a ledger outcome is uncertain; it does not promise that a failed attempt awarded the asset.

### Collectible spawn and pickup contract

- **Spawn formula.** Slot `i` gets reward `i % 6` in the order credits, uridium, galaxy energy, prometium, endurium, terbium. `seed = mapId*1709 + i*7919 + cycle*31`, `X = 2600 + seed % 15800`, `Y = 2200 + (seed*37) % 8700`. Every coordinate therefore stays inside `[2600, 18399] x [2200, 10899]`, and IDs are unique across maps 1..16. `Spawn` throws `ArgumentOutOfRangeException` for map IDs outside 1..16.
- **Cycle.** `cycle = unixSeconds / max(1, respawnSeconds)`. `world.collectibles.respawn_seconds` (default 300) sets `respawnSeconds`, `world.spawn.bonus_box_count` (default 6) sets the generated slot count, and `world.collectibles.pickup_radius` (default 180) sets the radius. Slots beyond the runtime count are neither visible nor collectible (`missing`).
- **Pickup order.** `CollectAsync` checks these in order and returns the first status that applies: an empty `AccountId` gives `invalid`, before the mutex is taken and before any wallet call. An ID that is neither a generated slot nor a manual admin box on the pilot's current map gives `missing`. A squared distance above `radius²` gives `distant`; exactly `radius²` is accepted, so the radius is inclusive. An existing cycle claim gives `claimed`. Ore that does not fit in the cargo hold gives `cargo_full`. None of these statuses changes visibility.
- **Claim key.** The key is `world:collect:{mapId}:{boxId}:{cycle}`. It is the cache reservation and also the wallet ledger idempotency key. It expires `respawnSeconds + 30` seconds after it is set. When the next cycle starts, the slot shows up again at that cycle's coordinates.
- **Reward multipliers.** Credits use `economy.credits_reward_multiplier` and uridium uses `economy.uridium_reward_multiplier`. The adjusted amount is `max(0, Math.Round(amount * multiplier))` with .NET's default round-half-to-even, so 5 × 0.5 gives 2 and 5 × 0.3 gives 2. Other assets ignore the multipliers. Only `Amount` changes, and the returned `Box` and the wallet credit both carry the adjusted amount.
- **Duplicate ledger.** If the wallet returns `false` (the ledger key was already applied), the result is `claimed`, nothing is broadcast, and the box stays hidden for the cycle.

## HTTP browser bridge

`GET /spacemap/world/state` and `POST /enter` return no-store `map` (ID/name/geometry/station/portals), `pilot` (identity/configuration/interpolated position/target/moveId/HP/shield/speed/laser/companions/radiation), `pilots`, `boxes`, `collectionRadius`, `npcs`, and optional `announcement`/`jump`. The `dosid` cookie authenticates. `POST /move` takes JSON `{x,y,configuration?,mapId?,expectedMoveId?}`; `/jump` takes `{portalId,mapId?}`; `/collect` takes `{boxId,mapId?}`; `/target` and `/fire` take `{npcId,mapId?}`; `POST /config` takes `{configuration,mapId?}`; `GET /config` reads current configuration. Stale map/revision yields HTTP 409 `map_changed`/`move_changed`; configuration cooldown yields 409 with `cooldownRemainingMs`; out-of-range/claimed/destroyed actions yield 409 statuses. Non-JSON writes yield 415, malformed JSON 400. The local page serializes same-kind commands, discards delayed old-map responses, and refreshes after conflicts. Admin world routes belong to SPEC-08.

The shared JSON media-type gate for `POST /move`, `/jump`, `/collect`, `/target`, `/fire`, `/config`, `/admin/command`, and `/admin/vars/rollback` compares the complete media type to `application/json`, ignoring ASCII case and surrounding whitespace before an optional semicolon-delimited parameter section. Thus `application/json; charset=utf-8` and `APPLICATION/JSON` are admitted. Prefix lookalikes such as `application/jsonp`, `application/json+xml`, and `application/json garbage` return HTTP 415. For the five movement and combat commands, this check occurs before session lookup or body reading. `WorldAndSpacemapSpecificationTests` checks their rejection and untouched bodies; `WorldHttpBridgeTests` checks an admitted move reaches state mutation. The architecture fixture pins all eight callers to one exact-match helper.

### Local spacemap page contract

`LocalSpacemapPage.Html` is the single self-contained document served by `IndexInternalStartEndpoint` for signed-in `internalStart`/`internalMapRevolution` requests. Fixture: `ThDarkOrbitEmulator.Tests/ClientTesting/WorldSpacemapPageSpecificationTests.cs`.

- **Document:** one `<html lang="en">` with UTF-8 meta and exactly one inline `<script>`. It loads no external resource: no `http://`/`https://` URL, `src=` attribute, `<link>` or `@import`. Element IDs are unique, and every declared control (`spaceCanvas`, `minimap`, the pilot readouts, `config1`/`config2`, `jump`, `fire`, `status`, `warning`, `announcement` and the `admin*` controls) is bound by the script. The `Menu` link targets `/indexInternal.es?action=internalWebGL&amp;from=internalStart`.
- **Transport:** there are exactly two `fetch` call sites. World commands use `/spacemap/world/{path}` and admin commands use `/spacemap/world/admin/{path}`. Both send `credentials:'same-origin'` and `cache:'no-store'`, and set `Content-Type: application/json` only when there is a body. Command shapes: `enter` (POST, no body), `state` (GET), `move` `{x,y,mapId,expectedMoveId}` (where `expectedMoveId` is the current `pilot.moveId`), `jump` `{portalId,mapId}`, `collect` `{boxId,mapId}`, `target`/`fire` `{npcId,mapId}`, `config` `{configuration,mapId}`. Admin calls are `vars`, `vars/history?limit=20[&beforeChangeId=N]`, `vars/rollback` `{changeId,reason}` and `command` `{text}`.
- **Errors:** a world HTTP 409 maps `map_lease_changed`, `map_changed`, `move_changed` and `distant` to fixed messages. Any other 409 status shows the raw `status` text, or, if there is none, `Configuration ready in ⌈cooldownRemainingMs/1000⌉s.`. The 409 status is stored as `error.status`. A non-409 401 shows `Session expired. Return to the menu and sign in.`. Any other failure shows `World request failed (N).`. Admin failures prefer the server's `error` text, fall back to `Admin request failed (N).`, and store the HTTP status.
- **Admin panel:** the panel is `hidden` in the markup and is shown in only one place: after `enter` succeeds with `pilot.isAdmin`. The command input has `maxlength=1024`. The reason input has `maxlength=256` and is `required`. A variable change or rollback with a blank trimmed reason shows a local message and sends no request. Variable sets are sent as `/var set {key} {JSON value} {JSON reason}`. History pages hold 20 rows. The cursor is the last row's `changeId`, `Load more` is hidden when a page has fewer than 20 rows, and a non-paged refresh resets the cursor.
- **Polling and interaction:** there is one `setInterval(refresh,150)` loop, and it skips a tick while a poll or move is in flight. The pickup radius falls back to 180 when `collectionRadius` is missing. Click coordinates are clamped to `[0,1]` of the canvas and then rounded to map units. An NPC within `max(260, 15·mapWidth/canvasWidth)` is targeted before any box within `max(250, 13·mapWidth/canvasWidth)` is considered, and targeting cancels any queued move or pickup. `Jump gate` picks the nearest portal by Euclidean distance, does nothing when the map has no portals, and ignores clicks while a jump is pending. A map change increments the map epoch and clears queued move, target and configuration commands, the pending box and the selected target. Configuration 1 starts `aria-pressed="true"`, and the button state then tracks `pilot.configuration`.
- **Rendering:** world text is written only through `textContent`. The page never uses `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write` or `eval(`. A kill summary lists only positive amounts, in the order credits, uridium, XP, honor, and falls back to `no currency`.
- **Placeholder branding:** the document has exactly one `<title>Spacemap - Space Emulator (Placeholder)</title>`. The served HTML contains no case-insensitive `DarkOrbit`, `Bigpoint`, or `bpsecure` token. `WorldSpacemapPageSpecificationTests` verifies the delivered HTML constant; `BrandingPlaceholderComplianceTests` verifies that the signed-in spacemap route writes that constant.
