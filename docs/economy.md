# Local economy foundation

The economy is emulator data only. It is used in Redirect mode and has no payment provider or world-entry behavior. Migrations `006_economy` through `012_admin_audit` create the economy schema, purchase currency selection, timed Tech Factory recipes, auction lots and bids, durable item-grant keys, craft progress, reward offers, and admin actor fields. The identity migration runner applies them on startup when auto-migration is enabled.

## Data and transaction rules

- `assets` is an admin-editable registry. Seeded currencies are `credits` and `uridium`; seeded resources are Prometium, Endurium, Terbium, Assembly components, Tech Factory components, and Galaxy Gate energy. `balances` stores nonnegative per-account amounts for both kinds.
- `ledger` records each nonzero balance change with a reason, menu source, idempotency key, delta, resulting balance, and timestamp. A database trigger rejects ledger updates and deletes. The `(account_id, idempotency_key, asset_id)` constraint rejects duplicate entries.
- `items` stores name, type, rarity, JSON stats, asset key, and enabled state. The seven existing Hangar starter items are seeded. `recipes` stores JSON input/output arrays, craft seconds, and enabled state; Assembly and Tech Factory recipes are seeded. `reward_offers` stores practice Payment and Voucher grants plus Quest and battle pass amounts, assets, targets, and enabled state. Migration `020_battle_pass_offers` seeds the three higher battle pass tiers (quartermaster, artisan, tycoon), so Postgres lists the same five tiers as the cache fallback.
- `listings` stores a JSON object of prices by currency, optional global stock, optional per-account limit, optional restock interval and amount, and enabled state. A null stock value means unlimited stock. Zero stock is sold out. Four existing Shop offers are seeded in credits. `purchases` tracks per-account quantities, `purchase_requests` records successful idempotency keys, and `stock_audit` records finite-stock purchases, admin adjustments, and scheduled restocks.
- Shop purchases run in one Postgres transaction. A buyer selects one listed currency, including Credits or Uridium; only that wallet is debited. An account advisory lock serializes wallet changes, and a listing row lock serializes stock changes across API processes. A failed debit rolls the entire purchase back. The database check constraints reject negative balances, inventory, and stock. Reusing a successful idempotency key with the same listing, quantity, and currency returns success without charging twice; reusing it for a different order fails.
- `pilot_skill_states` stores each account's Pilot Sheet ranks as a JSON object plus a revision; `pilot_skill_actions` records used allocate/reset form keys. Changes run under the account advisory lock, so a stale revision or a reused key is refused on every replica. The first Pilot Sheet access imports a cached skill state once, sanitized, and never overwrites an existing row (migration `021_pilot_skills`).
- `messaging_states` stores each account's Messages mailbox and friend list as a JSON object plus a revision; `messaging_actions` records used send/delete/friend form keys. Changes run under the account advisory lock. The first Messages access imports a cached mailbox once, sanitized, and never overwrites an existing row (migration `022_messaging`). Messaging never touches balances or inventory.
- `account_preferences` stores each account's Account center language, sound, and notification choices plus a revision (migration `023_account_preferences`). Saves run under the account advisory lock, so one `rev` applies once across replicas, and the revision wraps from 1,000,000 to 1. The first access imports cached preferences once, sanitized, and never overwrites an existing row; an unknown stored language reads as `es`. Preferences never touch balances or inventory.
- `hangar_selections` stores each account's active Dock slot (1 or 2; migration `024_hangar_selection`). Dock selections compare-and-set under the account advisory lock, so one signed form applies once across replicas. The first access imports a cached slot once and never overwrites an existing row; no row means slot 1. Selection never touches balances or inventory.
- `hangar_equipment_assignments` stores each account's Dock loadout (slot 1–2, configuration 1–2, item, quantity 1–999; migration `025_hangar_equipment`). Changes run under the account advisory lock against owned `inventory`, and assignments above owned stock are capped on read and on the next change. `hangar_equipment_imports` marks accounts whose cached assignments were copied (or that changed equipment first), so a cache copy is imported at most once. Equipment changes never touch balances or inventory.

The first Hangar access imports cached Credits, Assembly components, and item inventory once per account. The first Skylab, Tech Factory, and Galaxy Gates accesses separately import their cached resource balances. Subsequent Skylab production and upgrades, Galaxy Gate energy, and Hangar equipment operations reconcile through Postgres. Hangar inventory names, types, and quantities come from the item catalog and inventory tables. Assembly reads enabled database recipes and consumes inputs and grants outputs in one transaction; each signed craft form key is recorded in `craft_requests` (migration `019_craft_requests`) in that transaction, so replays craft at most once. Tech Factory reads timed database recipes, debits components at start, and credits the output resource at claim. Personal auction lots, bids, held Credits, and claimed item awards now persist in Postgres. Shop purchase and Assembly craft counts drive Quest and battle pass progress from Postgres. Practice Payment and Voucher grants, Quest and battle pass rewards, and expedition start debits use stable ledger keys; expedition and Space Search item grants use durable item-grant keys. The shared menu header shows every registered currency and resource balance. Menu caches still hold non-economic state such as equipment assignment, jobs, and claim display flags. Skylab collector levels and timing and Galaxy Gate parts persist in Postgres. Cache-only overloads remain for earlier unit contracts; routed Shop, Assembly, Auction, Skylab, and Galaxy Gates actions use Postgres.

## CMS administration

Migration `014_galaxy_gates` persists gate progress, and `015_skylab` persists collector levels, collection timing, and used action keys. Routed Skylab upgrades and collection change these records and shared resource balances in one account-locked transaction. Cache expiry cannot reset either menu's database progress.

Sign in with an `emulator-admin` realm role and open **Backoffice → Economy**. The catalog loads assets, items, recipes, listings, and auction lots. Save and error status appears at the top.

- **Items:** Select an existing item or enter a new ID. Fill name, type, rarity, and a JSON object in Stats JSON, such as `{"damage":10}`. Clear Enabled to disable an in-use item. Asset key is optional.
- **Crafting:** Select a recipe or enter a new ID and name. Add at least one input and output. For each part choose item, resource, or currency, its catalog ID, and a positive whole quantity. Craft seconds may be zero. The CMS serializes these parts into the API's `inputsJson` and `outputsJson` fields.
- **Assets:** Enter an ID, name, kind, and enabled state. Select Edit on an existing currency or resource to load it. Kind cannot change after creation; disable an in-use asset instead.
- **Shop:** Select a listing or enter a new ID and item, then set one or more currency prices. Blank initial stock is unlimited; zero is sold out. Set a per-account limit if needed. A restock rule needs both interval seconds and amount. Existing listing edits preserve stock; use Adjust stock for a signed delta or Set stock for a nonnegative target, always with an audit reason.
- **Account grants:** Enter an account UUID, load balances, choose a currency or resource, enter a positive whole amount and reason, and submit. Each grant uses a fresh idempotency key. The server records the admin subject.
- **Audits:** Select a finite listing for stock audit or enter an account UUID for its ledger. Filter by reason and, for ledger, by asset. Next page loads up to 50 earlier entries using the last displayed row ID.

The screens and API are emulator-only for Redirect mode; they do not process real payments or enter the game world. Listing reads include saved `restockIntervalSeconds` and `restockAmount` for the editor.

## Admin API

All routes below are under `/api/v1/economy` and require an authenticated Keycloak `emulator-admin` realm role. A viewer, operator, or permission-only token receives 403; no token receives 401. The route group is tagged “Economy administration” in OpenAPI. These are local admin operations; the Unity client does not call them.

The reviewable OpenAPI contract is [economy.openapi.yaml](economy.openapi.yaml). Recipe parts and price maps are serialized JSON strings in the current request DTOs.

| Method and path | Purpose |
| --- | --- |
| `GET /assets`, `PUT /assets/{id}`, `DELETE /assets/{id}` | List, upsert, or delete unused currency/resource definitions. The asset kind is fixed after creation. Disable assets that remain in use. |
| `GET /items`, `PUT /items/{id}`, `DELETE /items/{id}` | List, upsert, or delete unused items. `statsJson` is a JSON object. Items used by a recipe, listing, inventory, auction lot, or grant must be disabled instead. |
| `GET /recipes`, `PUT /recipes/{id}`, `DELETE /recipes/{id}` | List, upsert, or delete recipes. `inputsJson` and `outputsJson` are nonempty arrays of `{kind,id,quantity}` with known item or asset references; `craftSeconds` is nonnegative. |
| `GET /listings`, `PUT /listings/{id}`, `DELETE /listings/{id}` | List, upsert, or delete unused Shop listings. `pricesJson` maps enabled currency IDs to nonnegative unit prices. Existing stock is not overwritten by listing edits. Stock, account limit, and paired restock interval/amount are validated. |
| `GET /auction-lots`, `PUT /auction-lots/{id}` | List and upsert personal auction lot definitions, including item, opening bid, duration, and enabled state. |
| `GET /reward-offers`, `PUT /reward-offers/{source}/{id}` | List and upsert Payment, Voucher, Quest, and battle pass reward definitions. `progressKind` is `none`, `purchases`, or `crafts`. |
| `POST /listings/{id}/stock` | Add or remove finite stock with `{ "delta": 10, "reason": "admin_restock" }`; a negative result returns 409. The audit records the admin subject. |
| `GET /listings/{id}/stock-audit` | Page by `beforeId` and `limit` (default 50, maximum 200); optional `reason` filter. Entries contain admin subject when applicable. |
| `GET /accounts/{accountId}/balances`, `GET /accounts/{accountId}/ledger` | Read balances and page ledger by `beforeId` and `limit` (default 50, maximum 200); optional `assetId` and `reason` filters. |
| `POST /accounts/{accountId}/balances/{assetId}` | Apply `{ "delta": 100, "reason": "manual_grant", "menuSource": "admin", "idempotencyKey": "..." }`. The server fixes the source to `admin` and writes the Keycloak subject into the immutable ledger row. A duplicate key or insufficient balance returns 409. |

Write responses use 400 for invalid input, 404 for an unknown account/asset or missing deletion target, and 409 for a conflicting balance, stock, or in-use definition. Deleting a definition with foreign-key or recipe references returns 409; disabling it through PUT keeps past transactions readable. Successful upserts and deletes return 204. Audit pages are ordered by descending row ID; pass the last row's ID as `beforeId` for the next page.

The authenticated local Shop page reads listings, per-account purchases, inventory, and balances from Postgres. Its purchase form submits `item` (the listing ID), `quantity` (1–100), `currency` (a listed currency ID), and a per-form `idempotencyKey` to `POST /indexInternal.es?action=internalShopBuy`; all four fields are required exactly once. The key is signed with the session and listing and carries its issue time; keys older than one hour return 409 and must be refreshed by reloading Shop. It requires a live `dosid` and a selected company. Successful purchase returns 303; unavailable stock, limit, replay, or expired form returns 409; invalid or unaffordable requests return 400; non-POST requests return 405. No official post-selection Shop payload or Redirect client behavior has been captured.

## Remaining work

The CMS Economy page edits assets, items, recipes, listings, stock, auction lots, and account grants and reads ledger and stock audits. Reward offer editing remains API-only. Timed Tech Factory jobs remain in distributed cache. Claim status and the expedition start time recover from Postgres ledger and item-grant keys after cache expiry. Auction lots are personal practice lots, not a player market. Postgres integration tests cover concurrent stock purchase, retry, sold-out and disabled states, insufficient funds, currency choice, recipes, and auction claims; they were not run because the required container image may be outside the project boundary. All 192 non-integration tests and 7 CMS tests passed; the CMS development build also passed. Database-backed admin endpoint behavior and Redirect client use remain unverified. No Live capture was run because this task prohibits installing the mitmproxy CA.
